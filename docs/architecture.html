一個畫面切成幾層

官方只規定兩件事：拿 ViewModel 的那一層要跟排版的那一層分開，而且 ViewModel 不准往下傳—— 往下傳就沒辦法 preview。名字叫什麼不是官方的事。這裡採 Now in Android 的做法：同名多載。

外框

住在 :navigation，不在 feature 裡

Scaffold、TopAppBar、底部導覽。三個畫面共用同一份，所以外觀必然一致，標題與返回鍵由路由決定——路由本來就知道自己是誰。

Screen(title, onBack, bar) { padding -> ... }

有狀態

拿 ViewModel、collect、綁定

唯一碰得到 ViewModel 的地方。它不排版——只把流收下來、把方法接成 lambda，然後交給下一層。

FeedScreen(viewModel = hiltViewModel()) DetailScreen(viewModel = hiltViewModel()) SavedScreen(viewModel = hiltViewModel())

無狀態

同名多載．狀態往下分派

跟上一層同一個名字——「這兩個是同一個畫面的兩種形態」因此是編譯器層級的事實，而不是兩個碰巧相鄰的名字。它收 state 與 lambda，決定現在該畫哪一種，不知道 ViewModel 存在。

FeedScreen(stories, weather, onRefresh, onOpenArticle) DetailScreen(state, onRetry, onBack, onKeep, onLetGo) SavedScreen(state, onOpenArticle, onLetGo)

狀態葉節點

每一種畫面各自一個具名 composable。這一層存在的理由是 preview——一張圖剛好一個狀態，而且比 preview 整頁便宜也穩定。錯誤畫面因此不用拔網路線才看得到。

圖上看不到、但機器擋著的四條

架構如果只寫在文件裡，它就只是一個說法。這四條每一條都會讓 ./gradlew build 變紅。

沒有畫面看得到資料層

checkModuleDependencies 讀 Gradle 真實的邊。:feature:* 宣告 :core:data 就會失敗。

:app 碰不到任何 feature

它只認識 :navigation。而 :navigation 用 implementation 而非 api，所以型別也傳不過去。

:core:domain 是純 Kotlin

不是靠自律，是編譯器——那個模組沒有 Android SDK，寫了 import android.* 編不過。
